## Proposed v0.4 architecture

Propose one thin `HanumanBot` (`hanuman`) with the capability `hanuman.fetch`. Register it explicitly in the host's `BotRegistry`. The bot uses the existing `SpecialistBot` contract and delegates once through `BotContext.tools` to `shivax.hanuman.fetch`. An independent host registration helper adds the tool to `ProtectedToolRegistry`; the bot contains no transport. These identifiers and the target envelope are H00 design choices. `ToolRegistry.bind()` can reuse the same registered tool if a host later exposes it to a tool workflow through its own Vijay/Firewall policies. [Specialist base](../../src/bots/base.ts), [bot registry](../../src/agents/registry.ts), [tool registry](../../src/security/registry.ts), [workflow binding](../../src/workflows/registry.ts)

Keep HTTP clients, Playwright, general-purpose shell/file tools and deployment controls at the host boundary. Keep the Inspectra peer optional. Every registry, policy and budget belongs to an explicit host instance or run.

1. **Host composition.** The host registers the bot and the protected tool, supplies an immutable table of named HTTPS URLs and an egress transport, and binds NARASIMHA to the same Vijay before first use. It enables `hanuman.fetch` for the run, grants the exact tool ID when minting the Jay context, and supplies the task/workflow, bot and tool operation descriptors and mandatory allows. Give the tool descriptor the `hanuman` bot scope for the initial route. Importing either SDK entry or creating the default specialist system registers zero Hanuman routes and performs zero DNS or network I/O. A host registration alone grants zero permissions.
2. **Admission and dispatch.** Use `{ targetId: string }` and a fixed GET against the approved target for the authenticated scope. Configure read-only capability and tool policies, with explicit Vijay approval on the tool. Reject extra fields including raw URL, headers, credentials, query overrides, request bodies, redirect settings and budgets. RUDRA selects the explicitly registered specialist and Vijay grants a capability-scoped tool lease. Start with one call and zero retries.
3. **Protected egress.** Require live `checkExecution` and `checkNetworkAccess` callbacks from the bound tool lease. Check execution and the canonical destination before invoking the transport and recheck after resolution and immediately before connection. Configure exactly one matching operation for the tool and bot. Carry the leased signal through DNS, connect and streaming, with a narrower host deadline when configured. Missing protection fails before the transport runs. [RUDRA dispatch](../../src/agents/rudra/orchestrator.ts), [Vijay bot path](../../src/security/vijay.ts), [lease context](../../src/security/tools.ts), [firewall binding](../../src/security/firewall/runtime.ts)
4. **Completion.** The trusted transport disables redirects, credential forwarding and cookie handling, with any proxy explicitly configured by the host. Accept successful responses of supported media types (`text/plain` and `application/json`), carrying JSON as inert text. Bound wire and decompressed bytes, time and the final encoded `BotValue` envelope. Close or drain the stream on every exit and abort on failure or cancellation. Return `{ version: 1, targetId, status, mediaType, body, trust: 'untrusted' }`. Exclude headers, raw URLs and raw exceptions from projected metadata and logs. Content supplies zero authority and cannot become verified feedback or executable code.

## Security boundaries and regression risks

| Risk | Boundary and release requirement |
| --- | --- |
| Unapproved egress or authority injection | Sign-in, exact root context, explicit tool grant, capability allowlist, Vijay capability and tool policies, approval and mandatory firewall allow all stand independently. Tool input and upstream output are data. Keep fetch out of default planners, routing advice, model fallback and direct public execution helpers. An approved operation permits a named target for that run. Keep URLs, bodies, secrets and raw errors out of SDK audit events. |
| SSRF, rebinding, redirects and resolver discrepancies | NARASIMHA's callback checks HTTP(S) scheme, credentials and exact declared origin. It cannot observe the connected socket. The trusted transport must reject private, loopback, link-local, metadata, multicast and other non-public addresses including IPv4-mapped IPv6, verify IPv4/IPv6 DNS answers, pin a vetted destination through connection, preserve hostname/TLS verification, and enforce host/proxy egress. Block all redirects in the first release. Reject credentialed, non-HTTPS or deceptive canonical targets at registration. Browser code can consume a protected host broker only when that broker owns these checks. [Origin check](../../src/security/firewall/runtime.ts), [host boundary](../../SECURITY.md) |
| Revocation, cancellation and stale approvals | Reuse Vijay's post-approval verification and NARASIMHA's live checks. Jay stores grant snapshots and verifies provider revocation asynchronously at admission and approval. Have the host propagate in-flight session revocation through an abort signal or a revocation mechanism it controls. The transport must honor abort across DNS, connect, headers and body. SDK execution retains ownership until pending work settles, so a non-cooperative transport can delay cleanup. [Jay](../../src/security/jay.ts), [Vijay](../../src/security/vijay.ts), [lease draining](../../src/security/tools.ts), [session contract](../jay-vijay-security.md) |
| Resource exhaustion and concurrent admission | Enforce connection/read deadlines and cap wire and decoded bytes before buffering. Include serialized envelope overhead and cumulative run output limits. The initial RUDRA bot path can hold task, bot and tool leases simultaneously. Size firewall operation/concurrency limits for those leases, then test low limits and competing runs. Keep fetch-specific budget counters scoped to the applicable host run/realm. [Authorization](../../src/security/vijay.ts), [resource accounting](../../src/security/firewall/runtime.ts), [RUDRA limits](../../src/agents/rudra/orchestrator.ts) |
| Route and retry regressions | RUDRA selects the first eligible bot by ID by default. Use a distinct capability so registering Hanuman cannot change another bot's selection. The firewall rejects zero or multiple matching descriptors. Use zero retries in the initial fetch run and terminal existing error classifications for authorization and validation failures. Reuse `ToolRegistry.bind()` only when a separate host tool workflow needs the same service. [Workflow bindings](../../src/workflows/registry.ts), [RUDRA selection](../../src/agents/rudra/orchestrator.ts) |
| Prompt injection and unintended retention | Render or process bodies as inert data. Preserve untrusted provenance downstream and keep body content out of logging, authority fields, memory hooks and learning ingestion. If a host opts into persistence or model input, require its existing scope, privacy and governance controls. [Workflow outputs](../../src/workflows/engine.ts), [SARASWATI governance](../../src/learning/provenance.ts) |
| Package and downstream compatibility | Catch manifest/exported version drift, existing API or bot ID removal, split root/subpath class identities, ambient DOM/Node declaration dependencies, changes to worker loading, and optional-peer regressions. Re-run packed consumers without Inspectra and preserve the historical C01 matrix as a release comparison. [Package tests](../../tests/package.test.mjs), [SDK tests](../../tests/sdk.test.mjs), [C01 audit](shivax-inspectra-c01.md) |
